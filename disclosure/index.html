Disclosure / 開示方針

「見つけた」は、
報告の始まりです。

脆弱性を見つけたときに迷わないよう、窓口・対応目標・やめていただきたいことを先に置いておきます。報奨金はありませんが、返事を送る時間と、公開の相談は約束します。

1. 報告のしかた

相談窓口（メールアドレス）の設定と同時に、この章に宛先を表示します。それまでのあいだは、security.txt の Contact がこのページを指している状態です。窓口が未設置のあいだ送れないのが、正しい振る舞いだと考えています。

現時点で OpenPGP の公開鍵は置いていません。そのため、認証情報・顧客データ・生ログそのものは最初に送らないでください。「どの経路で、何が起きるか」を再現できる最小の手順だけで足ります。必要なものがあればこちらから個別にお聞きします。

報告に書いてあると助かること

対象のURLまたは機能・再現手順（リクエストとレスポンスの1組）・発生時刻・影響を受けそうな利用者・試していない追加の影響。スキャン出力の羅列より、通った1本の請求のほうが早く動けます。

2. こちらが引き受ける目標

下表は目標であり、保証ではありません。遅れる理由は必ず連絡します。対応は善意の報告があった場合を前提に、範囲を絞って進めます。

対応目標（確約ではなく目標値）
段階目安補足
初回連絡受け取ったことと、次に確認することを3営業日以内にお返しします。自動返信ではなく、人の目を通した1報目を約束します。
暫定評価影響範囲と重大度の暫定値を5営業日以内にお伝えします。この段階では確定させず、確認できた事実と仮説を分けて書きます。

開示の相談公開のタイミングは一緒に決めます。原則として修正確認まで待ちます。待機期間は90日を上限とし、それより早い公開も可能です。

3. やめていただきたいこと

以下は、報告として受け取っても対応の優先度を上げられません。代わりに、該当する手順を省いた形で送ってください。

  • 他の利用者やテナントに実際に影響を出す試行（書き込み・削除・送信を含む）。
  • データの持ち出し、大量の取得、権限昇格の状態を残すこと。
  • 従業員の騙し・総当たり・物理的な侵入の試行。
  • 許可のない環境への能動的なスキャンや、負荷をかける試験。
  • 修正が終わる前の公開・販売・SNSでの断定。

4. 法的な立場と謝礼

この方針に沿って善意で報告していただいた方を、報告そのものを理由として法的に問題視しません。ただし第三者が所有するシステムの検査は、その所有者の許可なく行わないでください。私の権限で代理の許可を出すことはできません。

報奨金（バウンティ）は置いていません。希望される場合だけ、報告者名・表記名・リンクを謝辞ページへ掲載します。掲載しない選択も可能です。

"This field MUST always be present and MUST NOT appear more than once."

RFC 9116 §2.5.5（Expires について）／同じ節は「1年より先を勧告しない」とも規定。

5. このページの根拠

  • RFC 9116 §2.5.3：security.txt の Contact は必須で、Web URI の場合は https:// で始まること。
  • RFC 9116 §2.5.1：謝辞（Acknowledgments）は報告者を認めるページへのリンクとして扱う。
  • 報告と対応の手順としては ISO/IEC 29147 および ISO/IEC 30111 が参照になります（規格本文は有料のため、ここでは名称だけ書きます）。
