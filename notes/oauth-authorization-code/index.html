Notes / OAuth 2.0

認可コードは、
あなたの要求から離れない。

「PKCE を有効にした」で止まるレビューと、検証が本当に効いているかを確認したレビュー。その差がどこに出るかを、RFC 9700 の原文に沿って追います。

  • RFC 9700 §2.1 / §2.1.1
  • RFC 7636 §4.1
  • 公開 2026-10-25

RFC 9700「Best Current Practice for OAuth 2.0 Security」は 2025年1月に発行され、RFC 6749・6750・6819 などに対して更新として位置づけられている Best Current Practice（BCP 240）です。かつて「推奨」と語られていた_PKCE_が、クライアントと認可サーバの双方に対して、かなり強い言葉で書き直されています。

この章では認可コードのバインディング——「発行された認可コードを、それを要求したブラウザセッションに結び付ける」一点だけに絞って、仕様・実装・テスト・仕様の沈黙という順に下りていきます。

1. 何が起きるのか

認可コードフローでは、認可サーバが発行した一時的な認可コードを、クライアントがバックエンドチャネルで /token に送ってトークンと交換します。このとき、認可コードそのものが「誰の要求に対して発行されたか」を覚えていなければ、コードを手に入れた人がそのまま交換できてしまいます。

1. 攻撃者のアプリが /authorize にアクセス（code_challenge なし）
2. 被害者のブラウザが認可画面に進み、認可コード C が発行される
3. C が攻撃者側エンドポイントに届く（既知の転送先・漏えい経路）
4. 攻撃者が自分の client credentials で /token に C を送る
→ トークンが攻撃者の手に入る

PKCE は、認可要求の時点でクライアントが持っていた値（code_verifier）のダイジェスト code_challenge を預かり、トークン交換時に元の値を突き合わせることで、この「拾った人がそのまま使える」状態を塞ぎます。

ただし PKCE は CSRF 対策ではありません

RFC 9700 §2.1 は、リダイレクトエンドポイントに対する CSRF を別途、クライアントが防ぐことを要求しています（"Clients MUST prevent Cross-Site Request Forgery (CSRF)"）。PKCE と state は守るものが違う、という整理を最初にしておくと、後の設計議論が楽になります。

2. 要求を、原文で読む

"If a client sends a valid PKCE code_challenge parameter in the authorization request, the authorization server MUST enforce the correct usage of code_verifier at the token endpoint."

RFC 9700 §2.1.1 Authorization Code Grant Clients（原文）

同じ節には、この一文のまわりにいくつもの MUST があります。レビューで確認するのは、いつもこの一覧です。

  • 認可サーバは PKCE をサポートしなければならない（"Authorization servers MUST support PKCE"）。
  • code_challenge が付いた認可要求に対しては、トークンエンドポイントで code_verifier の正しい利用を強制しなければならない。
  • 認可要求に code_challenge がなかった場合に code_verifier だけを送る要求を受け付けないことで、ダウングレード攻撃を防がなければならない（§4.8.2 参照）。
  • 認可サーバは PKCE のサポートを検出する方法を提供しなければならず、code_challenge_methods_supported の公開が推奨されている。
  • クライアントは verifier が認可要求に露出しない方式を使うべきで、現状それに対応するのは S256 だけだと明記されている（"Currently, S256 is the only such method."）。

3. 「導入した」で止まっている実装の穴

ライブラリが PKCE に対応していることと、このシステムで検証が効いていることは別物です。レビューで見かけるのは、だいたい次の4つです。

その1：チャレンジなしの要求も通してしまう

code_challenge が無い認可要求を黙って受け付ける設定が残っていると、攻撃者は最初から PKCE なしで作ればよくなります。BCP がダウングレードに別の MUST を置いているのは、この穴が現実的なためです。

その2：plain を受け付けている

code_challenge_method=plain は verifier をそのまま認可要求に流すため、「verifier を露出しない方式を使うべき」という §2.1.1 の趣旨から外れます。相互運用の事情で残す場合でも、リスクを書面で引き受けた記録が必要です。

その3：検証が例外経路で飛んでいる

正常系だけ通し、リフレッシュやフェデレーション、内部クライアントからの経路では検証をスキップしている実装は珍しくありません。トークンエンドポイントの分岐を全部列挙して、どの経路でも verifier に到達するかどうかを確かめます。

その4：使い捨てのはずの値を残している

code_verifier も code_challenge も、認証情報と同じ扱いの使い捨ての値です。デバッグログ・APM のトレース・フロントエンドのエラーレポートに載ってしまう構成は、防いだはずの経路から情報を落とします。

4. 負のテストを、先に決めておく

確認の手順は「正しい要求が通るか」ではなく「壊れた要求が拒否されるか」で書きます。以下は、この章の内容をそのままテストに落とした例です。

5. もう一つの錠前：リダイレクトURIの完全一致

"When comparing client redirection URIs against pre-registered URIs, authorization servers MUST utilize exact string matching except for port numbers in localhost redirection URIs of native apps."

RFC 9700 §2.1 Protecting Redirect-Based Flows（原文）

同じ節は、クエリパラメータから得た任意の URI へブラウザを転送するエンドポイント（オープンリダイレクタ）を、クライアントにも認可サーバにも置かないことを MUST NOT として要求しています。「自社ドメインだから許す」という運用が、ここで壊れます。仕様が例外として認めているのは、ネイティブアプリの localhost リダイレクトにおけるポート番号だけです。

6. 仕様が決めていないこと

深掘りの最後は、いつも「仕様が沈黙している場所」の整理です。ここが設計の判断になり、レビューの価値もここに出ます。

  • code_verifier の形は RFC 7636 §4.1 が決めています。英大文字・英小数字と - . _ ~ を使い、長さは 43 文字以上 128 人以下（ABNF: code-verifier = 43*128unreserved）。人力で考えられる文字列ではないので、必ず暗号学的な乱数から作ります。
  • challenge をどのくらい保持し、いつ捨てるかは規定されていません。認可画面での滞留時間と合わせて、許容する有効期間を決めておく必要があります。
  • トークンそのものをクライアントに縛る仕組み（DPoP や mTLS などの sender-constrained token）は PKCE と別の仕組みです。「PKCE を入れたから、盗んだアクセストークンは使えない」は正しくありません。

7. レビューでは、これを渡します

この章で触れた各項目について、私たちは次の4点セットで報告書に書きます。要求の位置（§番号と原文）、その設定値またはコードの分岐、拒否を確認した手順と実際の応答、そして同じ壊れ方を戻さないための回帰テスト案です。

仕様書の一行は、それだけでは何も守りません。検証できる問いに変わったときに、はじめて設計を動かせます。
